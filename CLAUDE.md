## Overview

An event ticketing platform for India: buyers discover events and book tickets (PayU or manual UPI), creators (organizers) run events and staff, staff sell tickets offline and scan QR codes at the gate, and admins approve creators and moderate the platform.

**Roles**
| Role | Table | How they log in | JWT payload |
|---|---|---|---|
| Buyer | `users` | `/login` (email/phone + password), `/auth/google` (Google ID token), `/social-login` (unverified, see C3) | `{sub, email}` (no `scope`) |
| Creator | `creator_accounts` | `/creator/login`; needs `kyc_status='Approved'` | `{sub, email, scope:'creator'}` |
| Staff | `staff_accounts` | `/staff/login` (login ID / email / phone) | `{sub, staffId, creatorId, scope:'staff'}` (no email) |
| Admin | `admin_accounts` | `/admin/login` | `{sub, email, scope:'admin', adminType:'admin'}` |
| Super admin | `super_admin_accounts` (separate table) | `/admin/login` (checked first) | `{sub, email, scope:'admin', adminType:'super'}` |

Purpose tokens use the same secret: `{scope:'password-reset', email}` (TTL `PASSWORD_RESET_TTL_MINUTES`, default 10) and `{scope:'signup-phone-otp', identifier}` (10 min). All login tokens last **30 days** (`server.js:168`).

**Main flows (as implemented today)**
- Buyer: signup → phone OTP (Twilio Verify) → `/signup` → browse `/events` → pick tier → PayU (`/payments/payu/initiate` → PayU → `/payments/payu/success`) **or** manual UPI ("I have paid" + UTR) → the browser itself calls `POST /bookings` → ticket with QR (`VYBERA-TICKET|bookingId|eventId|qrToken`).
- Creator: `/creator/applications` (+ KYC docs: pan/aadhaar/gst/bank) → super admin verifies every document and approves → `/creator/login` → `/creator/events` (goes **live immediately**, no event approval) → `/creator/staff` + `/creator/staff/:id/assignments` (allocates tier inventory to staff) → `/creator/analytics`, `/creator/finance/unlock` (4-digit PIN).
- Staff: `/staff/login` → `/staff/dashboard` → `/staff/sales` (cash/"online" sale, creates a booking) → `/bookings/scan` → `/staff/withdrawals`.
- Admin: `/admin/snapshot` (everything) → approve/reject creators & KYC docs (super only) → event status → user/staff status → admin accounts (super only).

## How to run locally

1. Node 20+, PostgreSQL (local or hosted).
2. `npm install`
3. Copy `.env.example` to `.env` and fill it in. **Required:** `DATABASE_URL`, `JWT_SECRET` (the server exits without them).
4. `npm start` → http://localhost:3003. `GET /health` checks the DB.
5. Schema = SQL files in `migrations/` (node-pg-migrate). The server runs pending migrations automatically **before** it starts listening; `npm run migrate` runs them by hand. Applied migrations are recorded in table `pgmigrations`.
6. **New DB change = new file** `migrations/NNNN_description.sql` with `-- Up Migration` / `-- Down Migration` sections. Never edit an applied migration, and never add startup `ALTER`s.

## Architecture

```
server.js                 entry point: load .env → migrations → data fix-ups → listen
src/app.js                Express app: global middleware, static files, route files in order
src/config.js             APP_BASE_URL, folders, JWT secret check
src/db/                   pool.js (shared pg pool), migrate.js, initDb.js (startup data fix-ups), queries.js (shared SQL)
src/middleware/           auth.js (requireRole, requireSuperAdmin, confirmed), security.js (CORS + CSRF),
                          rateLimit.js, audit.js
src/routes/               one Express Router per area: pages, creator, staff, adminAuth, admin, orders,
                          tickets, buyerAuth, auth (password + session lifecycle)
src/services/             business logic and outside services: orders, payu, sessions, staffWallet,
                          staffAssignments, passwordReset, adminAudit, signupOtp (Twilio), mail, storage (R2), tickets
src/utils/                small pure helpers: tokens (jose), cookies, accounts, events, serializers (row → JSON)
migrations/               versioned SQL migrations (node-pg-migrate)
public/index.html         live web SPA (all roles in one page, "pages" toggled by showPage)
public/firebaseconfig.js  Firebase Google sign-in helper (ES module, CDN imports)
public/                   the ONLY folder served by express.static (H1)
uploads/                  local file fallback (git-ignored, publicly served at /uploads)
scripts/                  build-cordova.js, check-html-escaping.js, reset-super-admin.js
test/                     integration tests (embedded Postgres + SMTP sink)
vybera-cordova/           Cordova Android project; www/ is generated, never edit it
```
**Layering rule:** routes handle HTTP (read the request, call a service, send JSON); services hold the logic and SQL and take `pool`/`client` as an argument where a transaction is involved; utils are pure. Nothing in `src/services` or `src/utils` requires a route file.

**Auth model (H5, since 2026-11-21):** see "Sessions" under Key design decisions. Middleware = `requireRole([roles])` in `src/middleware/auth.js`, built on `authenticateRequest` in `src/services/sessions.js`; token comes from `Authorization: Bearer` (app) or the `at_<role>` cookie (web, with `X-Session-Role` naming the role on multi-role endpoints).

**Request flow (original, partly superseded):** `cors` (reflects any origin) → a hand-written CORS/COOP middleware → `bodyParser.json({limit:'30mb'})` → `express.static(public/)` (fixed H1; previously the whole repo root) → routes. Auth is per-route middleware: `requireCreator`, `requireAdmin`, `requireSuperAdmin`, `requireStaff`, `requireBuyer`, `requireScanIdentity`, `requireProfileIdentity`. Tokens are sent as `Authorization: Bearer`. The frontend stores them in `localStorage` (`VYBERA_BUYER_TOKEN`, `VYBERA_CREATOR_TOKEN`, `VYBERA_STAFF_TOKEN`, `VYBERA_ADMIN_TOKEN`).

**Key tables** (schema in `migrations/`; descriptions below are from the Phase 1 audit, later changes are in the Issues log):
- `users`: buyers. `email` UNIQUE (case-sensitive); `phone` not unique; `status` Active/Suspended.
- `bookings`: PK `id TEXT`, **chosen by the client**. Has `user_id` (FK → users), `event_id` (**no FK**), price/qty/total, `status`, `qr_token`, `scanned_at`, `staff_id`, `staff_ref`.
- `creator_accounts` (+ `finance_pin`) and `creator_kyc_documents` (document type, object key, verification status).
- `creator_events`: PK `EVT-…`. `tickets` is a **JSONB array of tiers** `{name, price, qty, perks}`, where `qty` = tier inventory still unallocated to staff. `capacity` is never enforced. `booking_count`/`revenue` are denormalised and recomputed after sales.
- `admin_accounts` and `super_admin_accounts` (separate tables; legacy "Super Admin" rows are migrated over on boot).
- `staff_accounts`: `creator_id` NULL means admin-created staff. Login identifiers: `staff_id` (unique), `email`, `phone` (both non-unique). `share_token`.
- `staff_assignments`: tier inventory allocated to staff. `allocation_mode` is `creator_quota` (staff earns a commission) or `staff_owned` (staff resells), with `commission_rate`, `purchase_price`, `resale_price`, `sold_count`.
- `staff_sales` and `staff_withdrawals`.
- `payment_transactions`: PK `txnid` (**client-chosen**). Holds the PayU status and a `verified` flag. Not linked to bookings by any constraint.
- Indexes: see `migrations/0014_indexes.sql` (M2) plus those added with orders, sessions and the audit log. Schema history: `migrations/` (`0001_baseline.sql` = the old startup schema, unchanged).

## Frontend consolidation (M14), done 2026-11-21

- App-only CSS lives in `<style data-platform="app" media="not all">` blocks, placed at the same cascade position they had in the old Cordova file. The build script flips them to `media="all"`, so web styling is unchanged and the APK keeps its black/grey palette and mobile layout.
- App-only head scripts (`cordova.js`, `window.VYBERA_API_BASE`) are injected at the `<!-- CORDOVA_HEAD_INJECT … -->` marker.
- App-only JS stays behind `window.cordova` checks, so it is inert on web.

## Password recovery (D18, implemented 2026-11-21)
| Account | How the password is recovered | Code |
|---|---|---|
| Buyer | "Forgot password?" → emailed link (single use, 10 min) | `src/services/passwordReset.js`, `/auth/forgot-password`, `/auth/reset-password-by-token` |
| Organizer (creator) | Same emailed link (role `creator`) | same |
| Staff with email | Same emailed link; one link per account if several staff share the email | same |
| Staff without email | Their organizer (`POST /creator/staff/:id/reset-password`) or an admin (`POST /admin/staff/:id/reset-password`, re-confirm + audit) sets a temporary password; forced change at next login | `setTemporaryPassword`, `requireRole` → 403 `passwordChangeRequired`, `/auth/change-password` |
| Admin | Only a super admin: `POST /admin/accounts/:id/reset-password` (re-confirm + audit); next login = password → emailed code → forced change | same |
| Super admin | No self-service. On the server: `npm run reset-super-admin -- <email>` (prints a temporary password once, forced change, sessions ended, audited) | `scripts/reset-super-admin.js` |

Every reset ends all sessions of that account (token_version + refresh tokens). Temporary passwords are 12 random characters from an unambiguous alphabet, shown once, never stored in plain text.

## Key design decisions (existing, keep)

| Decision | Reason | Trade-off |
|---|---|---|
| `POST /bookings/scan` runs in a transaction with `SELECT … FOR UPDATE OF b`, checks the staff assignment, returns 403 (wrong event) / 409 (duplicate or refunded), and sets `scanned_at` | Two gates scanning the same QR at once: the second waits on the row lock, then sees `scanned_at` and gets 409. Only one entry. | Holds a row lock for the scan transaction (milliseconds). Whole booking (all qty) is admitted in one scan. |
| `qr_token = crypto.randomBytes(18)` (144 bits) | Unguessable, so a QR can't be forged even if the booking ID is known | Backfills in `/bookings/mine` use 24 bytes, which is inconsistent but harmless |
| **Sessions** (D7, H5): 15-min access JWT + 30-day rotating refresh token; web = httpOnly SameSite=Strict cookies per role, app = Bearer + secure storage | XSS can no longer steal a session; suspension / logout-everywhere take effect immediately via the per-request DB check of status + `token_version`; a stolen refresh token is detected when reused | One extra DB read per request (we already did one for status); 30 s reuse grace for parallel tabs; the app path depends on a Cordova plugin |
| **CORS allowlist + Origin check** (H16) | Cookies make cross-site requests dangerous; only our own origins may send credentialed requests | Any new frontend origin must be added to `CORS_ORIGINS` |
| Single-use reset links: version number in the token + compare-and-increment in one `UPDATE` | No token table needed; the row lock makes concurrent reuse impossible | Requesting a new link does not invalidate an older unused one until a reset succeeds (both carry the same version) |
| **Admin hardening** (H6): audit log, rate limit + lockout, email OTP, 5-minute step-up for destructive actions | Admin accounts can change everything, so they get every layer | More steps for admins; email OTP depends on the admin mailbox and SMTP being up |
| Versioned plain-SQL migrations run before `listen` | Every schema change is reviewable SQL with history; the app never serves requests on an old schema | Startup fails (by design) if a migration fails; a bad migration needs a new fixing migration |
| **Buying requires a logged-in buyer** (D9) | Simple ownership model: every order/ticket has a `user_id`, so C6 access control is one check | One extra step at checkout; softened by OTP signup and by returning the buyer to the same event + selection after login |
| **Orders hold seats for 15 minutes** (D10): event row locked (`SELECT … FOR UPDATE`) while counting `issued tickets + live holds + requested ≤ capacity` (and the tier pool) | Two buyers can never both get the last seat; nobody pays for a sold-out ticket | Lock serialises checkouts per event (milliseconds). Expired holds simply stop counting (no cron needed). A new checkout releases the same buyer's older hold for that event, so one user can't block an event with many open checkouts |
| **Late payment rule** (D10) | PayU can confirm after the hold expired | Re-check seats at callback time: room → `paid` + ticket; no room → `paid_needs_refund`, shown in Admin → Payments → Refunds; refund manually in the PayU dashboard until a refund flow exists |
| **Idempotent callbacks** | Gateways retry callbacks | Already-paid orders return success without re-issuing; unique index on `bookings.order_id` is the database-level guarantee |
| **Free tiers confirmed instantly** (D11) only when the DB price is 0 | No gateway needed for free events | Same inventory lock; max `FREE_TICKETS_PER_USER_PER_EVENT` (default 2) per user per event; `POST /orders` rate-limited per user and IP |
| **Referral credit via `share_token` only** (D12), fixed at order creation, paid out only when the order becomes paid | Nobody can credit an arbitrary staff member; no credit for failed payments | Must be active + assigned to that event and tier; self-referral (same email/phone) earns nothing; commission = subtotal × assignment `commission_rate`, stored as an `active` row that can later be `reversed` (refunds, M9) |
| **Server is the price authority** | Client-sent prices/totals were the root of C4 | Fee % / GST % / limits come from env and are published at `GET /config/public` so the UI shows the same numbers. Coupons are hidden until they exist server-side |
| **Postgres-backed fixed-window rate limiter** (`src/middleware/rateLimit.js`) | Works across restarts and multiple instances without Redis | Up to 2× limit around a window edge; fails open if the DB check errors. Needs `TRUST_PROXY_HOPS=1` on Render so `req.ip` is the real client |
| `requireAdmin` / `requireStaff` re-check account status in the DB on every request | A suspended account loses access immediately | One extra query per request |
| Twilio Verify issues a 10-minute, phone-bound signup token | The OTP state lives at Twilio; the server only signs "this phone was verified" | Token is reusable within 10 minutes (M17) |

## Study guide (read in this order)
Paths updated after the Phase 3 split (2026-11-22). Function names, not line numbers. Each area: files → what to look for → 3 likely interview questions.

### 1. Orders and seat holds (C4, H9, H11)
1. `migrations/0002_orders.sql`: order statuses, `bookings.order_id` unique index.
2. `src/services/orders.js`: `createOrder` → `lockEvent` (`SELECT … FOR UPDATE`) → `seatUsage` → `hasRoom` → `priceOrder` → insert; `resolveReferral`; `applyPayuResult` (late-payment rule, idempotency); `issueBooking`; `recordReferralCommission`.
3. `src/services/payu.js`: `makeRequestHash`, `makeResponseHash`, `isValidResponseHash` (constant time).
4. `src/routes/orders.js`: `POST /orders`, `handlePayuCallback` (303 redirect), `GET /orders/:orderId`.
5. `test/orders.test.js`: race tests, forged/mismatched callbacks, late payment.
- *Q: How do you stop two buyers getting the last seat?* — Both requests lock the same event row with `SELECT … FOR UPDATE` in a transaction; the second waits, then counts the first one's hold and gets 409. I proved the test is real by removing the lock: it fails every time.
- *Q: PayU confirms after the 15-minute hold expired. What happens?* — I re-check seats under the lock: if there's room the order is paid and the ticket issued; if not it becomes `paid_needs_refund` and shows up for admins to refund.
- *Q: Gateways retry callbacks. How do you avoid two tickets?* — Already-paid orders return success without issuing again, and a unique index on `bookings.order_id` guarantees it at the database level.

### 2. Ticket scan lock (keep-as-is design)
1. `src/routes/tickets.js` `POST /bookings/scan`: transaction → `SELECT b.* … FOR UPDATE OF b` → refunded/duplicate checks → `UPDATE bookings SET scanned_at`.
2. `requireScanIdentity` in `src/middleware/auth.js` (creator or staff) and the staff-assignment condition in the scan query.
- *Q: Two gates scan the same ticket at the same moment?* — The row lock makes the second scan wait; when it continues it sees `scanned_at` set and answers 409 duplicate. Only one entry.
- *Q: Why `FOR UPDATE OF b` and not just `FOR UPDATE`?* — The query joins events and assignments; `OF b` locks only the booking row, so we don't block unrelated work on the event.
- *Q: Why 403 vs 409?* — 403: the ticket is valid but this staff member is not assigned to its event. 409: the ticket was already used or refunded.

### 3. Sessions, refresh tokens, CSRF (H5, H16, L4)
1. `src/utils/tokens.js`: `jose`, issuer + audience per purpose.
2. `migrations/0004_sessions.sql`: `token_version`, `refresh_tokens`.
3. `src/services/sessions.js`: `authenticateRequest` (Bearer or cookie, DB status + `tv`), `startSession`, `rotateSession` (reuse detection + grace), `endSession`, `revokeAllSessions`.
4. `src/middleware/auth.js` `requireRole`; `src/middleware/security.js` (CORS allowlist, `blockCrossSiteCookieRequests`); `src/routes/auth.js` `/auth/refresh`, `/auth/logout`, `/auth/logout-all`.
5. `public/index.html` first script: `authHeaders`, `saveSession`, `refreshSession`, the `window.fetch` wrapper.
6. `test/sessions.test.js`.
- *Q: JWTs are stateless. How do you revoke one instantly?* — Every access token carries `tv` (token_version). Each request already loads the account to check its status, and compares `tv`; bumping the column kills all old tokens immediately.
- *Q: How does refresh-token reuse detection work?* — Refresh tokens rotate on every use and only their SHA-256 is stored. If an already-used token comes back (after a 30 s grace for parallel tabs), it must have been copied, so the whole login family is revoked.
- *Q: Why cookies on the web but Bearer tokens in the app?* — httpOnly cookies can't be read by JavaScript, so XSS can't steal them; the Android WebView calls the API cross-site where third-party cookies are unreliable, so the app gets tokens and keeps the refresh token in secure storage. Cookies bring CSRF risk, handled by SameSite=Strict, an Origin check and a CORS allowlist.

### 4. Staff withdrawals and cash (H10, D4)
1. `migrations/0005_staff_cash_settlements.sql`.
2. `src/services/staffWallet.js`: `staffWallet` (commission vs cash owed), `requestWithdrawal`, `recordCashSettlement`.
3. `src/routes/staff.js` `POST /staff/withdrawals`; `src/routes/creator.js` `POST /creator/staff/:staffId/cash-settlements`.
4. `test/wallet.test.js`.
- *Q: What was the double-spend bug?* — Balance check and insert were two separate queries, so parallel requests all saw the full balance. Now it's one transaction that locks the staff row first and recomputes the balance inside the lock.
- *Q: Why recompute inside the transaction instead of passing the balance in?* — A balance read before taking the lock can be stale; only a read made while holding the lock is guaranteed current.
- *Q: Why can't staff withdraw cash sales?* — That cash already sits with the staff member and belongs to the organizer; it's tracked as "cash owed" and settled by the organizer. Only commission is the staff member's money.

### 5. Admin hardening (H6, Q4)
1. `src/services/adminAudit.js`: `recordAdminAction`, `audited`; `src/middleware/audit.js` (`audit(...)` used on admin routes).
2. `src/routes/adminAuth.js`: `findAdminByEmail`, `registerFailedAdminLogin`, `startAdminOtpChallenge`, `POST /admin/login/verify`, `POST /admin/reauth`; `src/middleware/auth.js` `requireRecentReauth` (= `confirmed`).
3. `migrations/0006`–`0009`, `0011`; `src/services/passwordReset.js` `setTemporaryPassword`; `scripts/reset-super-admin.js`.
4. `test/admin.test.js`, `test/tempPassword.test.js`.
- *Q: Why the same message for a locked account and an unknown email?* — Different answers would tell an attacker which emails are real admins; we even run a dummy bcrypt compare for unknown emails so timing doesn't leak it.
- *Q: Why store the OTP hashed?* — If the database leaks, live codes can't be read. The code is also single use, expires in 5 minutes and dies after 5 wrong guesses.
- *Q: What does step-up confirmation add on top of a login?* — A session left open or hijacked can't do destructive actions without the password from the last 5 minutes; one fetch wrapper handles the prompt so no button had to change.

### 6. XSS output encoding (H7)
1. `public/index.html` first `<script>`: `escapeHtml`, `jsStr`, `jsArg`, `safeUrl`, `cssUrl`.
2. `scripts/check-html-escaping.js` (acorn-based check), `test/frontend.test.js`.
- *Q: Why isn't `escapeHtml` enough inside `onclick="…"`?* — The browser HTML-decodes the attribute before running it, so `&#39;` turns back into a quote and breaks out of the JS string; `jsStr` escapes for JavaScript first, then for HTML.
- *Q: What was wrong with `style="background-image:url(` + JSON.stringify(url) + `)"`?* — JSON.stringify adds double quotes, which close the `style` attribute and let a crafted URL inject new attributes. `cssUrl` uses single quotes and percent-encodes quotes and brackets.
- *Q: How do you stop this coming back?* — A parser-based check runs in `npm test` and fails the build when any value is put into an HTML string without the escaper for its context; it found 315 problems in the old file and finds 0 now.

### 7. Rules added after Phase 3 (event approval, verified phone, errors, fees)
1. Event approval: `migrations/0013_event_approval.sql`; `src/routes/creator.js` `POST /creator/events` (stores `pending`); `src/routes/admin.js` `/admin/events/:eventId/approve`, `/reject`, `eventNotReviewable`; `test/events.test.js`.
2. Verified phone: `migrations/0012_users_phone_verified.sql` (`phone_key`); `src/routes/buyerAuth.js` `/signup`, `PUT /profile/phone`, `/login` (verified phones only); `scripts/report-duplicate-phones.js`; `src/services/orders.js` `payablePhone`, the `phone_required` check in `createOrder`; `test/phone.test.js`.
3. Errors: `src/utils/httpError.js` (`HttpError`, `sendError`); the error handler at the end of `src/app.js`; `assertProviderSuccess` in `src/services/signupOtp.js`; `test/errors.test.js`.
4. Fees and paging: `organizerEarnings` and `ORDER_SETTINGS` in `src/services/orders.js`; `src/utils/paging.js`; `migrations/0014_indexes.sql`; `test/fee.test.js`, `test/paging.test.js`, `test/indexes.test.js`.
- *Q: Why is the approve query `UPDATE … WHERE id=$1 AND status='pending'` instead of read-then-write?* — The condition and the change happen in one statement, so if two admins click at once only one update matches and the other gets 409; no lock or transaction needed.
- *Q: How do you add a unique constraint when existing data might break it?* — Make the rule explicit (`phone_key`), stop new duplicates in code first, report existing duplicates for a human decision, and only then add the (partial) unique index. Otherwise the migration fails on deploy, or you silently pick a winner.
- *Q: Why not just return `err.message` on errors?* — It leaks internals (SQL, provider responses, config names) and gives attackers hints. `HttpError` marks messages written for users; everything else is logged with full detail while the client gets a generic message.

## Interview notes
_(One entry per fixed issue: a 2-line explanation to say out loud.)_

- **H1 static files:** "The server used `express.static` on the project root, so anyone could download `server.js` and internal docs. I moved browser files into a `public/` folder and serve only that, so the attack surface is an explicit allowlist instead of everything on disk."
- **M14 one frontend source:** "We had a web HTML and an APK HTML that had drifted by about 900 lines, so every fix had to be made twice. I merged them into one file. Platform-only CSS sits in a disabled style block that the Cordova build script switches on, so both platforms look the same as before but there's a single place to fix bugs."
- **C2 legacy password reset:** "There was an endpoint that changed any account's password if you just knew the email, including the super admin's. I deleted it and made the UI use the proper flow: we email a short-lived signed link, and only someone holding that link can set a new password."
- **C3 unverified social login:** "The Google login endpoint trusted whatever email the browser sent, so you could log in as anyone. Now the browser must send the ID token Google signed, and the server verifies Google's signature and that the token was issued for our client ID before creating a session."
- **C5 upload validation:** "Uploads had no login and no type check, so someone could upload an HTML file that ran as a page on our domain and stole tokens. I removed the unused upload routes, and the remaining ones check the file's real first bytes against an allowlist, cap the size, and pick the file extension themselves instead of trusting the browser."
- **C4 server-side orders:** "The browser used to send the price and say 'I paid', and the server believed it. Now the browser only says which ticket and how many; the server reads the price from the database, reserves seats under a row lock so two people can't buy the last seat, and only issues the ticket when PayU's signed callback is verified."
- **H11 overselling / race condition:** "I lock the event row with SELECT … FOR UPDATE, count sold tickets plus 15-minute holds, and insert the order in the same transaction. I proved the test is real by removing the lock: the eight-buyers-one-seat test then fails every time."
- **C6 ticket access:** "The ticket endpoint returned the QR code to anyone who knew the booking ID, and old IDs were just timestamps. Now one SQL query returns the ticket only if you're its buyer, the event's creator or assigned staff; everyone else gets the same 404 as a missing ticket, so you can't even tell which IDs exist."
- **H4 creator status check:** "The creator middleware only checked that the token was signed, so a suspended creator kept working for 30 days. Now every creator request also checks the account is still approved in the database, the same as we already did for admins and staff."
- **H13 creator login:** "Creator login matched by email, by name or by the part before the @, and told you whether the account existed. Now it's an exact email match, bcrypt only, one generic error for every failure, and a rate limit per IP and per email."
- **H2 single-use reset link:** "The reset link was a stateless token, so it worked again and again until it expired. I added a password_version column, put the version in the link, and the reset is one UPDATE that only matches the current version and increments it. The first use wins and every reuse finds nothing to update."
- **H3 OTP rate limit:** "Anyone could make our server send unlimited SMS codes, which costs money and can spam a victim. I added a Postgres-backed limiter: three OTPs per phone per ten minutes and ten per IP per hour, and the same idea for password-reset emails."
- **M20 one login endpoint:** "The login form sent whatever you typed to the admin, staff, creator and buyer endpoints one after another, so a buyer's password reached the admin login. Now you pick your role and the password goes to exactly one endpoint; I chose this over a server-side 'guess the role' login because one email can exist in several roles with different passwords."
- **H7 stored XSS:** "The frontend glued server data straight into innerHTML, so an event named with an img onerror tag ran script in every buyer's browser. I added escapers for each context (HTML text, JS inside onclick, URLs), applied them to about 300 places with a parser-based script, and added a test that fails the build if a new unescaped value appears."
- **H17 staff login matched the wrong account:** "Staff login also compared phone digits, and a login ID with no digits turned into an empty string that matched every staff member without a phone. I only compare phones when the input really has ten digits, prefer an exact login ID, and wrote a test that fails on the old code."
- **L4 jose:** "I replaced our hand-written JWT code with the jose library and gave every token an audience: session, password-reset or signup-otp. A token is only accepted where its audience matches, so a reset link can never be replayed as a login."
- **H5 sessions:** "Tokens used to live 30 days in localStorage with no way to revoke them. Now the browser gets a 15-minute access token and a refresh token in httpOnly cookies that JavaScript can't read, the refresh token rotates on every use and reuse revokes the whole login, and a token_version column lets me log an account out everywhere instantly."
- **H16 CORS:** "The server echoed back any Origin, which becomes dangerous once you use cookies. Now only our own origins are allowed with credentials, and any cookie-authenticated POST from another origin is rejected as CSRF."
- **H10 withdrawal double-spend:** "The balance check and the withdrawal insert were separate queries, so parallel requests all saw the full balance. Now it's one transaction that locks the staff row first, and I proved it with a test that fails without the lock. I also split money into commission, which staff can withdraw, and cash they collected, which they owe the organizer."
- **H6 audit log:** "Admin actions weren't recorded anywhere except the admin's own browser. Now every admin login and change is written to an append-only table with who, what, target, time and IP, by a middleware that only logs when the request actually succeeded."
- **H6 lockout:** "Admin login had no limit, so passwords could be guessed forever. Now it's rate limited per IP and per email, and five wrong passwords lock the account for fifteen minutes using one atomic UPDATE, with the same 'too many attempts' answer for real and fake emails."
- **H6 second factor:** "A correct admin password now only creates a short-lived challenge; the session starts after the six-digit code sent by email. The code is random, stored hashed, valid five minutes, single use, and five wrong guesses kill it."
- **H6 re-confirmation:** "Destructive admin actions like deleting an admin or suspending a user now need the password again within the last five minutes. The server answers 403 reauthRequired, and one fetch wrapper in the frontend shows the prompt and retries, so I didn't have to touch every button."
- **H12 cross-account email matching:** "The profile page matched a buyer's email to a creator account and showed that creator's events and revenue, and buyer emails aren't verified, so anyone could register with an organizer's email and see their sales. - **H14 KYC documents:** "The media route presigned any storage key without login, including Aadhaar and PAN scans. Now it only serves public folders like banners; KYC files go through a super-admin-only route that logs every view and redirects to a link that expires in sixty seconds."
- **H15 Cordova allowlist:** "The app's WebView was allowed to talk to any origin and navigate to dev tunnels. I replaced the wildcards with the exact hosts the app needs, and made the build fail if the backend URL isn't on that list, so a misconfiguration shows up at build time instead of as a broken app."
- **Q4 password recovery:** "Each account type has a recovery path that matches its risk: buyers, organizers and staff get a single-use emailed link; staff without email and admins get a temporary password from someone above them and must change it at the next login, enforced on every API call; the super admin can only be recovered with a script on the server."
- **M1 bootstrap overwrite:** "On every restart the server wrote the super admin password from an environment variable, which silently undid password changes. I made the bootstrap insert-only, and tested it by booting a second server against the same database."
- **L10 .env load order:** "Some modules read settings like the platform fee when they load, but the server loaded the .env file after requiring them, so local overrides were ignored. I moved the .env load to the first line and added a test that keeps it there."
- **Phase 3 split:** "I split a 3,900-line server file into routes, services, middleware and db modules, one area per commit, with the full integration suite green after every step. - **Q12 unique verified phone:** "One buyer account per verified phone, but Google users without a phone must still work, so the rule only covers verified, non-empty phones. Phones were stored in different formats, so I defined 'same phone' once in a SQL function used by the signup check, the duplicate report and the future partial unique index, and I report existing duplicates before adding the index instead of letting the migration fail or silently pick a winner."
- **Q6 event approval:** "Events now start pending and only an admin approval makes them public and bookable. The approve query only matches pending events, so two admins can't both act on one, and the second gets a 409. Re-approval only stops new sales: orders store their own price, and ticket viewing and gate scanning never depend on the event's status, so existing holders are unaffected. I wrote tests for both rules."
- **Q14 phone before payment:** "PayU needs a mobile number, and we used to send a fake one for Google users. Now a paid order without a phone is refused with a machine-readable code before any seat is held, the app asks once and saves it, then retries. A phone typed in that way is unverified, so I made sure it can't become a login name or replace a verified one."
- **M2 indexes:** "I indexed the columns the routes actually filter on, including expression indexes on LOWER(email), because a plain UNIQUE(email) index can't serve a case-insensitive lookup. The test turns sequential scans off and checks EXPLAIN uses each index, so an index whose expression doesn't match the query fails the build instead of silently doing nothing."
- **M4 pagination:** "I paged the public event list and buyer ticket lists with limit and offset, fetching one extra row to know if there's a next page. I deliberately didn't cap the admin snapshot, because the admin UI computes totals from it in the browser; cutting it would silently show wrong revenue. The right fix is server-side totals plus per-tab endpoints, so I listed that as future work."
- **M5 error messages:** "Errors are split into two kinds: HttpError for things the user can fix, with a message written for them, and everything else, which is logged in full while the client only gets 'Could not save'. A final Express error handler catches what routes don't, so even a malformed JSON body gets a JSON 400 instead of an HTML stack trace, and a test scans the code for the old err.message leak patterns."
- **M8 single fee constant:** "The fee was 8% on one screen and 6% on another. Now one setting feeds checkout, and one function turns it into the organizer's fee and net for every screen. A test runs the server at 10% so any leftover hardcoded number shows up. While doing it I noticed the buyer already pays the fee on top of the ticket price, so I raised whether organizers are being charged twice instead of guessing."
- **H18 test isolation:** "The test helper passed the whole environment to the server and the server loaded .env, so once a real .env existed, tests could have used the real storage bucket or mail account. Now the test environment is built from an allowlist-by-exclusion and the server is told to skip .env, with a test that checks real-service variables never reach a test server."
- **Q16 single-sided fee:** "The buyer pays the platform fee and GST on top of the ticket price, but the organizer's screens were subtracting the fee again from their ticket revenue, so the platform was effectively charging twice. Because M8 had already put that rule in one function, the fix was one function plus the screens that had their own copies."
- **L9 dead code:** "I found dead code mechanically: a function whose name appears only once in the file is never called, so I removed those and repeated until none was left. Functions declared twice were a trap: JavaScript hoisting makes the last declaration win, so the first copy never ran. One 'wrap the original' pattern even called itself forever because of that, which is how I found M21."
- **M21 staff Sell tab:** "The code saved the 'original' function in a variable and then redeclared it to add a feature. Because function declarations are hoisted, the variable already held the new version, so it called itself until the stack overflowed and staff couldn't sell at all. I gave the two functions different names, so the call order is explicit, and checked it with a real cash sale in the browser."
- **M22 data safety:** "The app used to 'fix up' data every time it started, including deleting legacy admin rows. Starting a server shouldn't silently rewrite someone's database, so startup now only adds what's missing, repairs became a manual script that does a dry run first, and a new column is interpreted with a SQL function instead of being backfilled. A test restarts the app and checks the rows are byte-for-byte the same."
- **M17 single-use token:** "A JWT is valid until it expires, so to make one usable once I gave it a unique id and record that id in the same transaction that creates the account. Two parallel signups race for the same id, and the primary key lets only one through. If the account insert fails, the rollback releases the id, so the user isn't punished for a typo."
- **M7 dev OTP:** "The development shortcut that returns the OTP in the response was switched on by the request's Host header, which a reverse proxy can set to localhost, so in a misconfigured deployment everyone could skip phone verification. It now needs an explicit flag that is ignored in production."
- **M4 admin totals on the server:** "The admin panel downloaded every booking and payment and added them up in the browser, so you couldn't page the lists without breaking the totals. I moved every total and chart series into SQL aggregates over all rows, and the lists now come 100 at a time with a 'Load more' button. Filters like the Pending tab run on the server, so they also find rows that aren't loaded yet."
- **M3 constraints on a live database:** "Adding constraints to a table that already has data normally fails or forces you to clean the data first. I added them NOT VALID, so Postgres enforces every rule from now on but never checks old rows, which means the migration can't fail and changes nothing. A read-only report lists the rows that break a rule, so the cleanup is a decision, not a surprise."
